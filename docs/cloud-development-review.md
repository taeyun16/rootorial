# 클라우드 개발 환경 검토

검토일: 2026-10-03

## 개발 서버 실행 결과

Codex 클라우드 작업 컨테이너에서 다음 명령으로 루토리얼 개발 서버를 실행했다.

```bash
npm run db:migrate:local
npm run dev -- --host 0.0.0.0
```

- 로컬 D1 migration은 이미 적용되어 있어 추가 적용 항목이 없었다.
- 개발 서버가 `0.0.0.0:3000`에서 수신하는 것을 확인했다.
- 컨테이너 내부에서 `http://127.0.0.1:3000/`에 요청해 HTTP 200과
  `Rootorial — 복잡한 기술을 바닥부터.` 페이지 제목을 확인했다.
- 해당 환경에는 Clerk 키와 관리자 allowlist가 없어 로그인·관리자 기능은
  별도 설정이 필요하다. 실제 값은 이 문서나 저장소에 기록하지 않는다.

위 결과는 검토 당시 실행 상태다. 환경 재시작 후에는 개발 서버를 다시 실행해야 한다.
서버 실행 옵션은 명령행으로 전달했으며 Vite 설정 파일은 수정하지 않았다.

## Tailscale로 3000번 포트에 직접 접근할 수 없는 이유

현재 Codex 클라우드의 Tailscale은 작업 컨테이너가 아닌 별도 사이드카에서
실행된다. 작업 컨테이너에는 Tailscale 인터페이스, `tailscale`·`tailscaled`
실행 파일, 표준 경로의 데몬 제어 소켓이 없었다.

`0.0.0.0`은 작업 컨테이너의 모든 IPv4 인터페이스를 의미하며, 사이드카의
Tailscale 주소까지 포함하지 않는다. 따라서 Tailnet의 온라인 노드 표시만으로
루토리얼의 3000번 포트에 접근할 수 있다고 판단할 수 없다.

```text
브라우저 → 사이드카의 Tailscale IP:3000
              ↓ 작업 컨테이너로의 인바운드 포워딩 없음
           루토리얼 개발 서버:3000
```

`tailscale serve`는 명령을 받은 데몬이 접근할 수 있는 백엔드를 프록시한다.
사이드카에서 지정한 `localhost:3000`은 작업 컨테이너의 localhost가 아니다.
작업 컨테이너에 CLI만 설치해도 사이드카 데몬을 제어하거나 이 경로를 만들 수 없다.

검토에 사용한 `cloud-environment-runtime`의 VPN 안내에 따르면 현재 통합은
클라우드에서 Tailnet 서비스로 접속하는 경로를 제공하며 인바운드 연결은 지원하지
않는다. 이는 Tailscale 자체의 Serve 기능 제한이 아니라 현재 클라우드 통합의 제한이다.

## 확인한 정책과 진단의 범위

- `/etc/codex/network-policy.json`에 `vpn_configured: true`가 있었다.
  이는 구성 여부이며 실제 VPN 통신 성공을 보장하지 않는다.
- HTTP 프록시 `proxy:8080`의 TCP 리스너에 연결할 수 있었다.
- Raw TCP CONNECT 경로는 `proxy:8088`로 설정되어 있었지만, 검사 당시 연결은
  거부되었다. TCP 허용 도메인과 IP 범위도 비어 있었다.
- 환경 상태 조회에서 제한된 HTTP 정책이 `enforced`인 것을 확인했다.
- 특정 Tailnet 서비스의 호스트·IP·포트에 대한 실제 요청은 수행하지 않았으므로
  아웃바운드 VPN 통신의 정상 동작 여부는 아직 검증하지 않았다.

`controlplane.tailscale.com` 등 HTTP 허용 도메인이나 아웃바운드 TCP 허용 대상을
추가하는 것만으로 개발 서버의 인바운드 포트가 공개되지는 않는다.

## 반복 설정을 줄이는 권장 운영 방식

### 개발용 Cloudflare Worker 자동 배포

루토리얼은 Cloudflare Workers 기반이므로, 별도 개발용 Worker와 D1 데이터베이스를
준비하고 개발 브랜치 push를 자동 배포로 연결하는 방식을 권장한다.

```text
Codex 클라우드에서 수정 → 개발 브랜치 push → 빌드·배포 → 고정 미리보기 URL
```

환경이 교체되어도 브라우저 접속 주소를 유지할 수 있다. 배포마다 빌드 시간이
필요하며 Vite HMR처럼 수정 즉시 반영되지는 않는다. 기존 `npm run deploy`는
운영 배포와 원격 D1 migration을 수행하므로 개발 미리보기용 경로를 별도로 구성해야 한다.

### HMR이 필요한 경우: 고정 Tailnet 기기와 역방향 SSH 터널

항상 켜진 Tailnet 기기에 클라우드가 먼저 SSH 연결을 열고 개발 포트를 역방향으로
전달하는 방식을 검토할 수 있다. 고정된 중계 기기 주소, 아웃바운드 TCP 허용,
터널용 SSH 인증, 중계 측 리스너와 필요 시 프록시 설정이 필요하다.

초기 설정 후 서버와 터널 시작·재연결을 하나의 스크립트로 묶으면 반복 작업을
줄일 수 있다. Vite 호스트 허용 및 WebSocket 전달도 실제 접속 경로에서 확인해야 한다.

두 운영 방식 모두 권장안이며, 이번 검토에서 미리보기 배포나 SSH 터널을
구현·검증하지는 않았다.
